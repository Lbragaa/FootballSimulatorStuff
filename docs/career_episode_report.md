# Career episodes — implementation and measured evidence

Ordinary Hikari continuation is now `play_next_episode {}`: one private command
issue and one final response. It orchestrates the existing Automatic/Controls/
lineage APIs. Regulation, world simulation, match seeds, checkpoint profiles and
historical regression hashes are unchanged. Existing commands retain their old
behavior; only the recommended client flow changes.

## What one request does

An episode first consumes accepted unseen pages, preserving every existing
cursor. Non-Vasco commentary is silent unless previously explicitly selected for
detail. With no unseen pages and automatic mode enabled, the coordinator uses a
deterministic UUID child to perform the existing next-day batch workflow. Each
child has its own exact parent, manifest, signed delegation, precommitted seeds,
execution receipts, independent replay/restoration and acceptance. It never
combines days into an unverified transaction or skips administrative obligations.

The first upcoming Vasco match receives recorded engine-selected XI/bench,
manager/formation/roles/rationale and every returned event through the final
whistle. The rest of its league round is handled silently when chronologically
safe. The 20-club table requires ALL recorded fixtures of the round final AND
fully revealed. A second Vasco match is a fence; an intervening cup milestone can
leave an explicitly partial round. No continental berth is awarded early.

A newly completed knockout stage waits for all of its legs' final pages, then
returns actual scores/aggregates, resolutions, qualified/eliminated clubs and
only activated draw records/known next-stage reservations. Mathematical title
and relegation notices use recorded 38-round and 17th–20th season rules, strict
point inequalities or the existing engine's champion record. Missing decisions
fail closed. Successful simulation alone does not approve a new sporting rule.

## Spoiler ordering and compactness

The canonical JSON serializer sorts object keys. Therefore match sections live
in an ORDERED `presentation` ARRAY, not independent top-level `fulltime` and
`timeline` fields. Hikari must render prematch, chronological events, final
whistle, fulltime/statistics/assessment, table and next fixture in that order.
No final score appears in the title/opening progress metadata. Goal score
snapshots are removed; each goal is narrated before its updated score.

Source events/page signatures remain unchanged locally. Presentation omits
duplicated on-field arrays, RNG fields and full individual performance dumps.
Actual starters/bench supply player-name mappings. Fulltime exposes team shots,
on-target and xG only after the signed final page. Halftime never ends an episode.
Luan Braga remains autonomous; Hikari must not cast the human as him or invent
quotes. [Concrete example](career_episode_example.json) uses explicit automated
test data; real rehearsal results stay private to avoid future-career spoilers.

Bounds: 35 calendar days, 16 internal batches, 120 revealed fixtures, 256 signed
20-event pages, 30 KB running presentation, 55 KB result, 60 KB signed transport,
and 900 seconds checked between atomic operations. A safe operation may finish
after the time threshold; it is never cancelled halfway. A progress-bound result
is explicit and resumable with a new ordinary continue. Its unfinished match/
round and unreported milestone baseline carry forward. Retrying an old UUID
always returns its original delivery.

## Recovery

`career-episode-1` signed local journals persist child UUIDs and page IDs BEFORE
effects. Acceptance before the episode-journal write resumes the SAME child;
page consumption before its journal write retrieves the SAME signed page.
The existing inbox/outbox seals one final response and handles uncertain posts.
New conversations can see a running request in status #1 before the long episode
finishes and must wait/read that issue instead of making a second command.

Known unresolved dependency failures expose a bounded blocker with agenda and
retained commitment ID, never raw exception paths/results. After correction, the
next episode adopts that exact child instead of selecting another seed. Unknown
integrity failures preserve the journal for local review rather than hiding them
as a successful football episode. Disable still blocks new batches; existing
committed work retains its original decision/results.

## Rehearsal benchmark

`tools/rehearse_episode.py` ran on disconnected private clones of the actual
accepted checkpoint above. It constructs no network transport/credential. The
original signed lineage still identifies its original career/mode inside the
clone; it is explicitly marked NONCANONICAL DISCONNECTED REHEARSAL, not relabeled
as a TEST authority or promotable successor. Key bytes are read into memory only,
not copied to the rehearsal or report. Clone accepted paths are redirected to
copied immutable packages. No rehearsal output is posted to GitHub or copied back.

A separate fresh clone injected a real interruption immediately after acceptance
and resumed the exact same episode request: **187.827 s wall time**, **15,836 B**,
**9 ms cached repeat**. The recovered and uninterrupted worlds were identical by
full world fingerprint and every fixture/result receipt hash: **52 total
receipts, one paid month-end** in both. This includes inherited accepted history;
there was no duplicated payroll, fixture or altered result after recovery.

The remainder is world/agenda/table inspection and orchestration. Existing core
execution/acceptance also validate internally; those checks are included in their
operation totals, not mislabeled pure match CPU. No replay/check is removed.
The main gain is eliminating 3–6 additional mobile/connector waits and using up
to 20 signed events per internal narration page. There is no separate roundup
command in an episode; its quiet consumption is included in narration time.

A real read-only private GitHub identity/repository/queue probe took 1.203 s.
Worker delivery journals separately record GitHub polling versus posting time;
they contain no command bodies, keys or results. Idle polling can be 5 seconds,
with a conservative header-based rate-budget backoff up to 300 seconds. Identical
status bodies avoid repeated read/write cycles; repository/account validation
still occurs at every poll and before effects. No paid/always-on service is added.
