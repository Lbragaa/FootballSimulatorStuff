## Performance and storage

On the **same accepted generation-3 snapshot** (145,678,336-byte DB), full
multi-season verification took 221.28 s wall / 109.47 s CPU. Immediate-parent
verification took 42.15 s / 36.50 s: **80.95% less validation wall time**, with
identical logical state. Both authenticate files, validate history/schema and
independently compare every table. The signing key is the explicit parent-
attestation trust boundary. This is one paired snapshot, not an episode speedup.
Full ran first; filesystem warmup may favor rolling. Cumulative process peak was
169.8–171.8 MB, not an isolated per-phase memory measurement.

Historical receipt loading across all 1,341 matches now selects receipt hashes
and resolution only, instead of whole squads/events/performance JSON. Identical
projected values took 0.375 s rather than 1.240 s; selected text fell from
137,437,424 to 845,159 bytes. This is a reporting workload, **not** complete
episode latency. The second query benefits from filesystem warmup.

Immutable compressed chunks/Merkle indexes retain one materialized head and
deduplicate successive databases. No full raw DB is stored in every accepted
payload. Portable export authenticates every reachable object; fresh restoration
independently replays the final suffix. Full-history audit remains available.
Limits are explicit: 2 GiB per file, 8 GiB portable archive, 250,000 objects.
Reaching a limit fails closed; indefinite unbounded storage is not promised.

The eight earlier compact DEV archives were streamed and verified against every
recorded member SHA256 without extraction. All remain byte-for-byte intact.
Completed scratch tests and benchmark copies were removed. The final run retains
one compressed TEST evidence package, not working/exported/restored DB triplets.

Three consecutive **fresh** two-group 2029 successors measured 124.79, 110.37
and 423.66 s end to end (69.67, 70.17 and 81.77 s CPU) on development Windows /
Python 3.14 / OneDrive. These precede the final bounded-memory and duplicate-scan
repairs. They expose substantial host/I/O variance and are not an instant-play
claim. Phase timings are in the [rehearsal evidence](validation/registered_season_rehearsal.json).
Pool content grew from 91,371,396 to 93,537,704 to 95,854,052 bytes, instead of
retaining another complete raw database per acceptance.

Final restoration first exposed an actual `MemoryError` in full-object table
encoding. Fingerprinting now streams the **identical frozen double-encoded row
contract**, spilling bounded sorted runs only for large tables. Every existing
table hash on the final 330,018,816-byte world matched; fresh-process structural
validation peaked at 55,246,848 bytes RAM. A separate complete-history portable
audit then passed in 529.98 s wall / 488.19 s CPU, with 231,321,600-byte peak.
The retained package is 98,247,067 bytes. No raw rehearsal DB copies remain.

Independent replay is still performed. Exact replay DB byte identity can prove
all-table equality directly; different SQLite layouts fall back to the original
logical table comparison. Parent fingerprints computed and authenticated within
one validation call are reused within that call only. Neither is a cache of
successful verification. No match output/hash/seed changed.

Phone episode timings in the final resumed run are explicitly **cached delivery**
measurements, not original simulation latency. Real GitHub network/poll delays
were not measured; the transport was disconnected. No live iPhone/production
deployment test is claimed for this new candidate.
