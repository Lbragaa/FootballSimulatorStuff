# Task 03B plan — official persistence and the global calendar

Historical planning document. The development-only implementation is now described in [Task 03B report](task03b_report.md) and [world architecture](world_integration.md); [Task 03C](task03c_plan.md) covers remaining calibration, draw/rule decisions and the official-play gate. No official execution has been authorized or performed.

No work in this plan is permission to execute an official match. Task 03A leaves accepted 046C v2 at 2027-09-26 23:30, all September 30 continentals pending and Mirassol–Vasco R26 unplayed. Save numbers must represent accepted chronological checkpoints, not implicitly one Brasileirão round each.

1. **Resolve missing source data and rules first.** All 16 September 30 fixtures have at least one foreign club without recorded players. Obtain commissioner-approved fictional squad/identity/rating evidence or an explicitly approved modeled-roster policy, preserving original history and source provenance. Do not import current real-world squads or replace missing players silently. Specify registration, suspensions, aggregate orientation, extra-time/shootout/away-goal rules and tie-breaking per competition. Confirm the forward engine/configuration/seed policy before official execution.
2. **Add versioned adapters.** Implement `CompetitionAdapter` for league, Copa do Brasil, Libertadores and Sudamericana. Map `league:ID` and legacy cup-table keys into unique global fixture identities. Preserve observed season versus fictional kickoff date. Confirmed matches can execute; conditional reservations cannot acquire fictional participants until qualification is recorded. `Progression` supplies aggregates, tie-resolution needs and next fixtures; the match core remains competition-agnostic. Extend the engine for extra time/penalties only under explicit competition rules and a forward version.
3. **One player timeline across competitions.** Add reviewed immutable player-state observations, injury onset/recovery eligibility, disciplinary/registration state, training consumption and elapsed-time recovery policy. A club playing twice in a week must not receive two blanket weekly recovery bonuses. Snapshot each kickoff after all earlier authorized state deltas, not from the same old checkpoint for an entire round. Preserve the archive #196/#354 distinction and all existing identities.
4. **Chronological agenda and execution claims.** Build a global ordered due-event agenda beginning September 30, before October 3 Vasco. Include month-end administrative obligations without treating a league round as the clock. Lock accepted parent and claim execution IDs with parent/input/config/seed hashes **before** draws. Store a unique receipt per global fixture; reject final/claimed fixtures and incomplete/ambiguous squads. A crash retries the identical commitment or resumes a stored result, never allocates a favorable new seed. Explicit user authorization must name the official agenda/batch and engine version.
5. **Scratch-only atomic apply.** Register a reviewed additive migration for execution/config/snapshot/shot/event/stint/receipt tables and legacy table mapping. Purely simulate, independently validate, then apply the approved forward delta in one disposable SQLite transaction. Recompute standings and qualification from recorded facts. Player statistics, fitness, injuries, suspensions and coach state must reconcile. Roll back the whole batch on failure. Protect every settled parent record and all unrelated finance/identity fields.
6. **New portable candidate profile.** Define the next version only when authorized; do not pre-create Save 047 in Task 03A. Audit exact permitted forward changes against the immutable accepted 046C parent while retaining the original 046 baseline. Export a portable checkpoint containing config/input/seed commitments, receipts, full ordered engine results, operation before/after images, narration cursor and validation evidence. Verify independent restoration before atomically publishing a fresh directory and requiring exact-hash acceptance. Keep binaries in durable release/storage assets rather than accumulating them in Git.
7. **Verification and integration.** Test duplicate application, two concurrent runners, crash after commitment/simulation/validation/transaction/export, locked or altered parents, late/same-time events, regulation draws/two-leg ties/ET/shootouts, chronology across competitions, recovery overlap and month-end payroll idempotency. Preserve canonical results across replay and Hikari cursor restarts. Require Windows/Linux CI with exact accepted inputs and zero unauthorized history changes before requesting official execution.

The Phase 2A pure agenda helper and adapter/player-state protocols provide boundaries only. There is no implied official persistence, artificial aggregate winner, foreign player prior or calendar skipping behavior in the current engine.
